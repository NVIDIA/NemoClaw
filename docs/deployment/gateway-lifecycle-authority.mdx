During onboarding, exactly one component owns the OpenShell gateway lifecycle.

Platform images sometimes supervise the gateway with their own service.
If onboarding does not know that, both layers can try to control the same gateway and port.
Onboarding can replace the live listener, and the platform service can restart it.
The host then has a persistent bind conflict and no authoritative owner.

The gateway-management contract makes that ownership explicit for onboarding.
NemoClaw manages its gateway, or it attaches to a gateway that an external supervisor owns.
When external supervision is declared, onboarding does not silently start a NemoClaw-managed gateway.

<Warning>
The declaration controls gateway effects in `nemoclaw onboard`, including preflight, resume, rebuild, and onboarding recovery paths.
It does not change gateway cleanup in uninstall or sandbox-destroy commands.
Do not run those cleanup actions against an externally supervised gateway.
</Warning>

## Management modes

| Mode | Onboarding behavior |
|---|---|
| `nemoclaw-managed` | NemoClaw manages the packaged gateway service or a standalone gateway. The platform must not add a second gateway implementation. |
| `externally-supervised` | NemoClaw validates and attaches to the platform-supervised gateway. Onboarding does not start, stop, or replace its process. |

When nothing is declared, NemoClaw keeps its historical behavior.
It manages the packaged gateway user service when installed, or it manages a standalone gateway.

## Declare the mode

Point `NEMOCLAW_GATEWAY_MANAGEMENT` at a JSON file:

```bash
export NEMOCLAW_GATEWAY_MANAGEMENT=/etc/nemoclaw/gateway-management.json
```

```json
{
  "version": 1,
  "mode": "externally-supervised",
  "endpoint": "http://127.0.0.1:8080",
  "stateDir": "/var/lib/openshell/gateway",
  "supervisor": {
    "kind": "systemd-system",
    "serviceName": "openshell-gateway.service",
    "execPath": "/usr/local/bin/openshell-gateway"
  },
  "requiredCapabilities": ["sandbox.create"]
}
```

| Field | Meaning |
|---|---|
| `version` | Contract version. Only `1` is supported; an unrecognized version fails rather than being ignored. |
| `mode` | `nemoclaw-managed` or `externally-supervised`. |
| `endpoint` | Bare HTTP origin where the gateway listens. Contract v1 rejects HTTPS because it does not define TLS trust material. Use a numeric IPv4 or IPv6 loopback address. DNS names such as `localhost` are rejected so resolver configuration cannot redirect the readiness probe off-host. The origin must not contain credentials, a query string, or a path. Its port must match `NEMOCLAW_GATEWAY_PORT`. |
| `stateDir` | Absolute path of the gateway state directory. |
| `supervisor` | Required for `externally-supervised`, and rejected for `nemoclaw-managed`. `kind` is `systemd-system` or `systemd-user`. `serviceName` and an absolute `execPath` are required. NemoClaw checks the listening process against both values. |
| `requiredCapabilities` | Optional list of capabilities that onboarding needs. Supported values are `gateway.health`, `sandbox.create`, `sandbox.exec`, and `gpu.passthrough`. An unsupported value stops onboarding before any effect. |

<Note>
Contract v1 supports only systemd supervisors.
NemoClaw uses cgroup membership to bind the listener to the declared unit.
The contract rejects a supervisor that cannot provide this ownership proof.
</Note>

<Note>
OpenShell exposes no gateway capability-discovery endpoint.
NemoClaw checks `requiredCapabilities` against the capabilities that its build implements, not the running gateway.
This check rejects a platform profile that requires a capability from a newer NemoClaw build.
</Note>

<Note>
The declaration must not contain credentials.
NemoClaw rejects unknown fields instead of ignoring them.
It persists ownership metadata and emits that metadata in diagnostics and machine events.
</Note>

## What externally supervised mode enforces

Before onboarding changes provider, policy, sandbox, or registry state, NemoClaw checks that the declared owner still holds the gateway.
Onboarding stops without starting a competing gateway when:

- the declared endpoint names a port this process does not operate the gateway on;
- the declaration requires a capability this NemoClaw build does not implement;
- the declared supervisor is not active;
- nothing is listening on the gateway endpoint;
- an unrecognized process holds the gateway port;
- more than one process holds the port, so ownership is ambiguous;
- the listening process is not part of the declared supervisor unit;
- the listening process cannot be bound to the declared unit at all;
- the declared authority would change part-way through a run (that is an explicit migration, not a silent switch);
- the running gateway is not the declared executable;
- the listener set cannot be enumerated, so a second gateway cannot be ruled out;
- the supervised gateway is running but does not answer a health check.

These checks run on a fresh onboarding attempt and on resume.
A recorded `complete` gateway step does not prove that the declared owner still holds the port.
The same guard protects the shared gateway start entry point and each onboarding recovery branch.
Rebuild and recovery cannot start a gateway on Docker-driver or non-Docker-driver hosts.

## Fix a failure

Resolve an externally supervised gateway failure through the platform supervisor:

```bash
systemctl status openshell-gateway.service
```

Start the supervised gateway and leave exactly one process holding the port.
Then run `nemoclaw onboard` again.

To return lifecycle control to NemoClaw, remove the platform gateway service.
Then declare `nemoclaw-managed` or remove the declaration.
