# Onboarding lifecycle contract map (#6225, epic #6224)

Characterization map of the onboarding and runtime-mutation journeys: where desired state comes from, what is validated before effects, where the first visible and first destructive effects happen, what is checkpointed, where the credential boundary sits, and what compensation exists today. It records current behavior, including behavior the epic flags as a contract gap; nothing here is a target design — targets live in #6226/#6227/#6228 and `machine/README.md`. References are stable symbol + module names, never line numbers.

Companions: `README.md` (file placement for the `onboard.ts` split), `machine/README.md` (FSM architecture and handler contract), `src/lib/messaging/AGENTS.md` (the messaging package these journeys cross into).

## Vocabulary

Epic terminology (from #6224, use verbatim): a **lifecycle contribution** is an internal, data-first input to a plan (policy, provider, package, port-forward, resource, runtime setup), not a public SDK. A **managed agent package** is a package recorded as desired state for an agent runtime; the user-facing managed OpenClaw package lifecycle is #5998's scope, not this epic's. An **agent-native plugin** is interpreted by OpenClaw/Hermes/another agent runtime. **NemoClaw plugin SDK** is reserved for a future versioned external contract that must not be claimed before the #6229 decision record.

| Verb | Meaning | Current artifact |
|---|---|---|
| intent | Deterministic, serializable desired outcome recorded before any effect; logical bindings (env-var names, presence flags), never secret values, temp paths, or handles | `SandboxCreateIntent` (`sandbox-create-intent-types.ts`), produced by the pure `resolveSandboxCreateIntent` (`sandbox-create-plan.ts`) |
| plan | Intent plus observed state, ready to execute; serializable (`SandboxMessagingPlan`) or execution-bound (temp paths, callbacks) | `MessagingWorkflowPlanner.buildPlan` (`src/lib/messaging/compiler/workflow-planner.ts`); `materializeSandboxCreatePlan` (`sandbox-create-plan.ts`) |
| apply | The effectful phase; capabilities (credential values, live handles) bound at apply time, never stored in intent or checkpoints | `bindMessagingTokenDefs` (`sandbox-create-plan.ts`) rebinds real tokens at materialization and fails on drift |
| checkpoint | Durable, secret-free record a later run can resume from | Onboard session (`~/.nemoclaw/onboard-session.json`, `src/lib/state/onboard-session.ts`) + machine snapshot; pre-recreate workspace backups; rebuild backup manifest |
| result | Explicit handler outcome: advance, retry, branch, complete, failed | `OnboardStateResult` (`machine/result.ts`), applied via `OnboardRuntime.applyResult` and the `OnboardRuntimeBoundary` facade (`runtime-boundary.ts`) |
| compensation | Effects after failure/cancel that undo a partial journey | Failed-create sandbox deletion in `createSandbox`; `cancel-rollback.ts`; `rollbackChannelAdd` (`src/lib/actions/sandbox/policy-channel.ts`); rebuild recovery-registry restore (`rebuild-recreate-phase.ts`) |
| reconcile | Re-aligning recorded and live state without a full re-run | Drift detection in `createSandbox`; `reconcileSandboxMessaging` (`machine/handlers/sandbox-messaging.ts`); `mergeOpenClawRestoredConfig` (`src/lib/state/openclaw-config-merge.ts`) |

## Machine states

13 states (`machine/definition.ts`); the transition table (`machine/transitions.ts`) is the linear advance chain plus the `inference -> provider_selection` retry, the `sandbox -> openclaw | agent_setup` branch, and every non-terminal state `-> failed`. One production owner per non-terminal state: `machine/handlers/preflight.ts`, `gateway.ts`, `provider-inference.ts` (composite for `provider_selection` + `inference`), `sandbox.ts` (resume decision in `sandbox-resume.ts`, messaging reconciliation in `sandbox-messaging.ts`), `agent-setup.ts` (`openclaw` + `agent_setup`), `policies.ts`, `finalization.ts` (`finalizing` + `post_verify`). `init` is advanced by `onboard()` before the first slice; `complete`/`failed` are terminal. The FSM is deliberately step-granular (`machine/types.ts`): mid-operation resume inside gateway startup, sandbox creation, credential upserts, or policy application is out of scope — the root of several checkpoint gaps below.

## Journey contracts

| Journey | Entry point | Desired-state source | First destructive effect | Durable checkpoint |
|---|---|---|---|---|
| 1. Sandbox create (fresh onboard) | `onboard()` (`src/lib/onboard.ts`) | Flags + env + prompts of the current run | None against prior state; creation itself at `streamSandboxCreate` | Whole-step session + machine snapshot |
| 2. Rebuild / installer upgrade | `rebuildSandbox` (`rebuild-pipeline.ts` via the `rebuild.ts` facade) | Registry entry + matching session only; ambient env quarantined | `openshell sandbox delete` (`rebuild-destroy-phase.ts`) | Backup manifest + session rewritten as recreate contract + recovery registry snapshot |
| 3. Re-onboard / resume over existing sandbox | Same `onboard()`, live-sandbox block of `createSandbox` | Current run's env/flags/prompts; registry + gateway as drift baseline | Delete + `docker rmi` + registry removal inside `createSandbox` | Pre-recreate workspace backup + session |
| 4. Runtime mutation (provider switch, config set, channels, plugin entries) | `inference-set.ts`, `sandbox/config.ts`, `policy-channel.ts` | CLI flags + registry/session metadata; per-channel delta plans | None in-place; channel changes defer destruction to a queued rebuild | Audit entries + registry plan persistence |

**Journey 1 — fresh create.** Options resolved by `resolveOnboardEntryOptions` (`entry-options.ts`, auto-resumes an in-progress session); messaging plan compiled by `MessagingWorkflowPlanner.buildPlan` and transported via env `NEMOCLAW_MESSAGING_PLAN_B64` (`MessagingSetupApplier.writePlanToEnv`, `applier/setup-applier.ts`). First externally visible effect: gateway reuse/recover/start (`startGateway`); inference-provider credential upserts (`upsertProvider`) run in `provider_selection`/`inference`, before any sandbox exists. Messaging-provider upserts run with `replaceExisting: true` inside `materializeSandboxCreatePlan`, overwriting same-name entries in shared gateway state. Checkpoints: whole-step session (8 fixed steps, atomic tmp+rename save) plus machine snapshot via `OnboardRuntimeBoundary`; registry registration deferred to post-ready (`registerCreatedSandbox`, `sandbox-registration.ts`) to prevent phantom entries; no sub-step checkpoint. Credential boundary: session stores `credentialEnv` as a name only, redacts `endpointUrl` at save, keeps legacy credential migration as sha256 hashes; intent carries presence flags and env keys, never values; real tokens rebound at apply by `bindMessagingTokenDefs`, fail-closed on availability or provider-type drift. Compensation: readiness failure deletes the failed new sandbox; build-context temp dirs (which can hold env-arg API keys) are cleaned inline with a process-exit safety net; two-key cancel rollback is armed only for a brand-new sandbox and clears the session when it fires (`cancel-rollback.ts`); nonzero exit marks the last started step failed (`exit-step-failure.ts`). Known gap: process death between gateway provider upserts and sandbox create leaves gateway credential state changed with no sandbox. Non-interactive runs share this contract, substituting env defaults and hard aborts (`non-interactive-abort.ts`) for prompts.

**Journey 2 — rebuild, including installer upgrade** (`upgradeSandboxes` in `src/lib/actions/upgrade-sandboxes.ts` calls `rebuildSandbox(name, ["--yes"], { recoveryManifest, ... })`). Desired state comes from the registry entry + matching session only (`prepareRebuildResumeConfig`, `rebuild-resume-config.ts` — the #5735 pre-delete trust boundary; custom-endpoint URLs fail closed if recorded only in another sandbox's session); ambient `NEMOCLAW_*` selection env is quarantined by `isolateAmbientRecreateEnv` (`rebuild-env-isolation.ts`); messaging is restaged from the registry-persisted plan (`stageRebuildMessagingPlanOrBail` in `rebuild-messaging-phase.ts` -> `buildRebuildPlanFromSandboxEntry` in `workflow-planner.ts`). All validation precedes destruction: `runRebuildPreflightPhase` (`rebuild-preflight-phase.ts`: registry snapshot pinned and re-asserted after confirmation, gateway schema, recovery-manifest validation, confirmation, onboard lock), then `prepareRebuildTargetPreflights` (`rebuild-preflight-target-phase.ts`: target config, recreate options, messaging plan staging, then the #5954 conflict preflight `preflightRebuildMessagingConflicts` with forced non-interactive abort, runtime and base-image checks). DCode rebuilds additionally prebuild and fingerprint the replacement image pre-delete (#6214, `prepareDcodeReplacementBeforeMutation` in `rebuild-dcode-preflight.ts`); mutation-edge revalidation runs immediately before deletion (`revalidatePreparedRecoveryBeforeDelete` in `rebuild-pipeline.ts`; `revalidateDcodeReplacementAtMutationEdge`). First destructive effect: `openshell sandbox delete` in the destroy phase (`rebuild-destroy-phase.ts`), then registry entry removal (entry kept when MCP entries exist, as the durable MCP rebuild transaction). Checkpoints: workspace backup manifest (`runRebuildBackupPhase`, `rebuild-backup-phase.ts`, or a validated installer manifest); session rewritten wholesale as the recreate contract with preflight/gateway pre-marked complete (`rebuild-recreate-phase.ts`); registry snapshot for recovery recreates. On a failed recreate: `markLastStartedStepFailed`, registry-snapshot restore for recovery recreates only, backup path preserved with manual `snapshot restore` instructions, MCP registry restore, shields relocked in the pipeline `finally`. Known gaps: a plain (non-recovery) recreate failure leaves no registry entry; non-DCode rebuilds build the replacement image only after deletion.

**Journey 3 — re-onboard / resume.** Two sub-modes share `onboard()`: the live-sandbox block of `createSandbox`, and the `--resume` decision `decideSandboxResume` (`machine/handlers/sandbox-resume.ts`: create / reuse / recreate / repair-and-recreate). Desired state is the current run's env/flags/prompts; registry and gateway are only a drift baseline (agent, provider migration, live-probe selection, GPU, Hermes tool-gateway and dashboard, messaging credential rotation). Restore intent (#6130) is keyed on installer env `NEMOCLAW_RESTORE_LATEST_BACKUP_ON_RECREATE=1` (`selectPreUpgradeBackupForCreate` / `resolveNotReadyOutcome`, `not-ready-recreate.ts`); without it a non-interactive not-ready sandbox blocks with hints. Pre-delete validation: the messaging conflict guard, a CPU-sandbox-vs-GPU-request reuse guard, interactive confirm gates, redirection of MCP-managed sandboxes to `rebuild`, and resume conflicts (`getResumeConfigConflicts`, `resume-config.ts` — the recorded sandbox name counts only when the sandbox step completed, #2753) which exit before any effect. Terminal machine snapshots are repaired only per `classifyResumeMachineRepair` (`resume-repair-policy.ts`: failed, or inconsistently reopened complete) by `repairResumeMachineSnapshot` (`resume-machine-repair.ts`). Checkpoint: fail-closed `backupSandboxBeforeRecreate` (`sandbox-backup-on-recreate.ts`; a failed backup aborts unless `NEMOCLAW_RECREATE_WITHOUT_BACKUP=1`; skipped when a pre-upgrade backup is already selected or a not-ready recreate is in progress). Compensation: workspace restore after create; default-sandbox restoration deferred to post-create (#4614); cancel rollback deliberately not armed for recreates; no registry snapshot restore — a failed recreate relies on session + backup + `onboard --resume`. Known gaps: resume identity when the sandbox step never completed (#5961/#5783); interrupted snapshot shapes outside the two repaired classes (#6040); the delete-then-create window below.

**Journey 4 — runtime mutation.** All mutation is host CLI; the `nemoclaw` OpenClaw plugin TUI is read-only. (4a) Provider/model switch: `runInferenceSet` (`src/lib/actions/inference-set.ts`), serialized by a timer-bound shields mutation lock; validates provider allowlist, model-id charset, registered-agent match, shields-down, and local-provider reachability before any write; writes are ordered and forward-only — gateway route -> registry -> API-family refresh -> in-sandbox config patch (non-fatal) -> session -> audit; no rollback, `rebuild` is the documented repair for degraded states. (4b) Config change: `configSet` (`src/lib/sandbox/config.ts`); dotpath validation, shields-down, `gateway.*` refusal, scalar-ancestor/array clobber refusal, new-key confirmation (#2400), and SSRF validation with DNS-pinned rewrite, then a sha256 compare-and-swap write under the sandbox mutation + shields locks; fail-closed CAS, no compensation needed. (4c) Channels add/remove/start/stop (`addSandboxChannel`, `removeSandboxChannel`, `sandboxChannelsSetEnabled` in `policy-channel.ts`): per-channel delta plans from the registry entry (`workflow-planner.ts`); `checkChannelAddConflict` is a hand-rolled mirror of the onboard conflict guard that uniquely offers `--force` (detection errors fail closed unless forced; pre-enable hook registry-read failures fail soft); gateway upsert/detach, preset apply, and registry plan persistence run immediately but destructive apply is deferred to a queued rebuild (`promptAndRebuild`); compensation via `rollbackChannelAdd`, re-disable on a failed `channels start` preset, a QR-channel remove hard-stop before registry mutation (#3998), and `syncSessionPolicyPresetsWithRegistry` so a later rebuild resume does not revert presets. (4d) Plugin entries (`plugins.entries.*`): written by manifest render targets and the web-search flow at build/rebuild; reconciled at restore by `OPENCLAW_CONFIG_RESTORE_OWNERSHIP` (`openclaw-config-merge.ts`: current generated entries win by id, backup-only user entries kept); direct edits go only through `config set` gates; no plugin CLI (#5998's scope).

**Agent differences.** The FSM branches `sandbox -> openclaw` for OpenClaw and `sandbox -> agent_setup` for other agents; both rejoin at `policies`. DCode is the only agent with pre-delete replacement-image validation on rebuild (#6214) and is excluded from messaging (no channel manifest supports it; `channels add` rejects it pre-mutation). Hermes adds tool-gateway and dashboard drift axes plus its own rebuild credential preflight.

## Create-path ordering contract

Inside `createSandbox` (`src/lib/onboard.ts`), on the shared create/recreate path. This prose is the authoritative record of the ordering; per cv review of PR #6259 it deliberately has no source-scanning test — executable coverage belongs to the issue that introduces a behavioral seam (#6226/#6228).

1. **Validation order (all deterministic work before any destructive effect):** `validateName` fixes the sandbox name; `prepareSandboxMessagingPreflight` (`sandbox-messaging-preflight.ts`) resolves disabled channels, runs the shared conflict guard `enforceMessagingChannelConflicts` (`messaging-conflict-guard.ts`) against the env plan (only when that plan names this sandbox) with the onboard-specific interactive "Continue anyway?" wiring, and aborts when a selected web-search credential is missing from the process; drift detection, reuse fast paths (which return before the destructive boundary — a reused sandbox is never deleted), and interactive confirm gates follow; then `selectPreUpgradeBackupForCreate` (`not-ready-recreate.ts`) and the fail-closed `backupSandboxBeforeRecreate` (`sandbox-backup-on-recreate.ts`).
2. **Conflict guard before delete:** the messaging conflict guard is the #5954 contract on this path — it completes before the destructive boundary, unlike pre-#5955 rebuild.
3. **Destructive boundary (recreate only), strictly ordered:** `runSandboxProviderPreDeleteCleanup` -> `openshell sandbox delete` -> `docker rmi` of the previous image -> `registry.removeSandbox`.
4. **Cleanup before upsert, post-delete:** `prepareSandboxCreatePlan` (`sandbox-create-plan.ts`) runs after the delete, so the pure `resolveSandboxCreateIntent` and the fail-closed credential-binding check in `materializeSandboxCreatePlan` (`bindMessagingTokenDefs`) validate only after the old sandbox is gone — a binding drift halts all gateway writes but cannot restore the sandbox (pinned gap, #6226). Inside materialization the tolerant provider-cleanup re-run (`tolerateMissingSandbox: true`; the sandbox no longer exists) precedes the gateway messaging upsert (`replaceExisting: true`). Then `streamSandboxCreate`, the readiness gate (`waitForCreatedSandboxReadyWithTrace`; failure deletes the new sandbox — the only other delete call site — and exits with retry hints), post-ready `registerCreatedSandbox`, and the pending workspace-backup restore.
5. **Delete-then-create window:** between `registry.removeSandbox` and post-ready `registerCreatedSandbox` there is no durable record of the selected sandbox identity; process death in this window leaves neither a sandbox nor a registry entry (checkpoint gap; #6228).

## Persisted state and field ownership

`~/.nemoclaw/onboard-session.json` is owned by `src/lib/state/onboard-session.ts` and written through `OnboardRuntimeBoundary` during onboard; rebuild rewrites it wholesale as the recreate contract. Step helpers default to record-only (`RECORD_ONLY_STEP_MUTATION_OPTIONS`, `src/lib/state/onboard-step-mutation.ts`); `LEGACY_MACHINE_STEP_MUTATION_OPTIONS` remains the escape hatch that also moves the machine snapshot (exit backstop, rebuild). The registry is owned by `src/lib/state/registry.ts`; the machine snapshot `{version, state, stateEnteredAt, revision}` by `OnboardRuntime`. Pinned ambiguity, not endorsed: `null` is overloaded across session fields (unset vs declined vs cleared); explicit-clear semantics exist only for the `filterSafeUpdates` whitelist (the #2625 null-vs-undefined contract in `onboard-session.ts`); explicit modeling is #6228's mandate, sandbox-identity nullability is #5783/PR #5860.

## Divergences (duplicated decision points)

Recommended owners name where a single decision should live; alignment belongs to the referenced child issues.

1. **Messaging desired state has four sources by path** — onboard env plan (`MessagingSetupApplier.writePlanToEnv`), rebuild registry plan (`buildRebuildPlanFromSandboxEntry`), resume-reuse fallback chain in `reconcileSandboxMessaging` (recorded channels -> env plan -> registry plan -> `session.messagingPlan`), single-channel deltas for mutations; owner: the registry-persisted plan (#6226/#6228).
2. **Ambient env polarity is inverted** — onboard treats `NEMOCLAW_PROVIDER`/`MODEL`/`ENDPOINT_URL` as intent; rebuild quarantines exactly those (`isolateAmbientRecreateEnv`) and pins intent from registry + session (`prepareRebuildResumeConfig`, #5735); owner: one target-resolution module (#6226).
3. **One conflict-guard engine, three wirings** — onboard interactive continue (`enforceMessagingChannelConflicts`), rebuild forced non-interactive abort (`preflightRebuildMessagingConflicts`, #5954), channels' hand-rolled `checkChannelAddConflict` with `--force`; owner: `messaging-conflict-guard.ts` taking per-path policy declaratively.
4. **Backup/restore intent differs per path** — rebuild always backs up and auto-restores including presets; re-onboard backs up fail-closed but restores only workspace state; the not-ready path restores only under the installer flag (#6130); channel mutations checkpoint nothing; owner: one backup/restore policy module (#6228).
5. **Registry lifecycle asymmetry** — create registers post-ready only; rebuild removes at destroy and snapshot-restores only for recovery recreates; re-onboard removes with no snapshot restore; owner: `sandbox-registration.ts`; durable pre-create identity is #6228.
6. **Pre-delete replacement validation exists only for DCode rebuilds** (#6214, `rebuild-dcode-preflight.ts`); non-DCode rebuilds build the real image after deletion, onboard/re-onboard entirely post-delete; full build-verify-swap atomicity is #5801's scope, outside this epic.
7. **Policy-preset reconciliation exists only on rebuild** — onboard writes `appliedPolicies` once at registration; channel commands mirror presets via `syncSessionPolicyPresetsWithRegistry`; owner: the `policy-preset-persistence`/`policy-preset-sync` modules.

## Merged and in-flight work

- **PR #6218** (merged) separated the secret-free `SandboxCreateIntent` from effectful materialization and kept the `prepareSandboxCreatePlan` compatibility surface; it deliberately did not move intent resolution ahead of the destructive boundary, persist intent, or define a machine-event/public contract — those are #6226, #6228, #6229.
- **PR #6214** (merged) added DCode pre-delete replacement validation (#6195); **PR #5955** (merged) moved the rebuild messaging conflict check before destruction (#5954).
- In flight — do not treat recovery/resume semantics as frozen: **PR #6253** (recovery-path refactor toward #6227; coordinate before touching `resume-machine-repair.ts`, `session-bootstrap.ts`, `machine/transitions.ts`, `exit-step-failure.ts`), **PR #6116** (dashboard-forward rollback scope, #6099), **PR #5860** (null sandbox identity, #5783).
