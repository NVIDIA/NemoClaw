# PR Review Advisor repair

This directory implements the manual Phase 1 flow from [issue #10791](https://github.com/NVIDIA/NemoClaw/issues/10791). A maintainer can bind one already-produced PR Review Advisor result to an exact same-repository PR head, let Pi propose one offline patch, validate that patch independently, and publish a GitHub-verified commit through deterministic code. The workflow is default-disabled, manual-only, and has no automatic trigger.

## Trust boundaries

The `collect` job re-fetches an open, non-draft, same-repository PR into `main`; requires the PR author to be the Phase 1 pilot `cjagwani` with current maintain or admin permission; binds that author through selection and validation; independently requires both the original and triggering actors to have maintain or admin permission; verifies the maintainer-supplied exact head SHA and successful `pull_request_target` Advisor run; and requires exactly its context artifact plus all nine specialist artifacts by immutable artifact ID and digest. Each specialist supplies a canonical exact-head finding ledger. The context includes complete issue-comment, submitted-review, and inline-thread state within enforced item limits. A body longer than 4,000 characters is represented by its beginning and end around an explicit truncation marker, but its full GitHub text remains bound by a per-body SHA-256 digest. The canonical review-state digest covers the bounded text, every full-body digest, and the remaining resolution metadata; missing, partial, or over-limit state fails selection. The maintainer selects canonical finding IDs, never free-form finding text, and trusted code rejects IDs absent from those ledgers. Finding text, PR metadata, specialist output, review text, and repository contents remain untrusted data. Validation and publication recheck the pilot author, PR identity, and review-state digest. Publication also rechecks maintain or admin permission for the pilot author and both dispatch actors, then re-fetches every immutable Advisor artifact identity. The one-shot attempt identity is the accepted exact-head tuple of repository, PR, head and base SHAs, Advisor workflow/run/attempt, and sorted selected finding IDs. Artifact IDs and digests, opt-in authority, product-scope evidence, selected paths, the finding-ledger digest, and the review-state digest are separately bound into the selection and validation receipts and rechecked at every publication boundary, but cannot create a second attempt for the same approved tuple.

The `claim` job has only read permissions plus `checks: write`. It creates one neutral check run whose external ID is the attempt identity and rejects an existing identical claim. It does not execute PR code, receive a model credential, or publish source changes.

The full workflow uses one non-cancelable concurrency group per PR. A later dispatch can wait behind an in-progress attempt, but it cannot interrupt a claim, the bounded Pi conversation, trusted validation, publication, or generated-head verification. Every run still rechecks the live head at its trust boundaries, and publication uses compare-and-swap, so a queued attempt that has become stale fails closed rather than updating the branch.

Trusted selection permits only explicitly named source, test, or documentation paths. It excludes workflow, agent-instruction, security-policy, dependency, lockfile, tooling, and E2E paths, along with findings that need credentials, attestations, external mutation, product decisions, DCO, or commit-verification work.

The `repair` job exports the exact PR tree without `.git` metadata or symbolic links. Pi receives two fixed turns inside one offline OpenShell sandbox with only `read`, `edit`, `write`, `grep`, `find`, and `ls`: one repair turn followed by one self-review and finalization turn. The in-attempt Pi session and transcript stay inside the disposable sandbox and are never downloaded or retained. Pi receives no PR, head, base, workflow, run, artifact, commit, attempt-digest, or receipt identity; GitHub token; model credential; shell; Git; test runner; package manager; commit capability; or publication tool. Trusted host code binds the final untrusted proposal to the exact attempt and source head, compares the returned tree with the original export, and creates the Git patch itself. Changes outside the selected exact-path allowlist fail closed. The two turns share the existing 20-minute model budget; there is no later Pi retry after trusted validation.

The `validate` job reconstructs the exact head independently, rechecks that the live PR head and base have not changed, applies the bounded patch with hermetic Git settings, and rejects special Git objects, binary content, dependency/control paths, credential-shaped content, and receipt mismatches. It also refuses any PR whose original diff changes workflows, agent instructions, security policy, dependency inputs, lockfiles, tooling, CI controls, or E2E files. Host code may install only base-controlled dependencies with lifecycle scripts disabled and an explicit public registry. All repository checks then run inside a second pinned, offline OpenShell sandbox with no model or GitHub credential. The candidate checkout is writable, while its `.git` metadata and installed dependency trees are mounted read-only. Validation must not mutate the approved candidate. The job deletes the sandbox and gateway before rechecking the live PR identity and emitting a trusted receipt and validated patch artifact. The patch-containing validation bundle expires after one day; a receipt-only copy remains for 14 days.

The `publish` job is the only source-writing job and is protected by the `advisor-repair-publication` environment. It starts only when the validator emits an explicit trusted `validated` outcome, so rejected, blocked, and no-change attempts never enter the protected environment. It never receives the model credential, untrusted Advisor artifacts, or the earlier selection artifact. It downloads only the validator's exact same-run artifact ID without a repository or run override. Trusted code strictly parses that self-contained receipt, recomputes the approved exact-head attempt identity, verifies every separately bound Advisor artifact, authority, scope, finding, and path field, reconstructs the validated Git tree with hermetic Git settings, and confirms every path, status, mode, type, and byte count before creating a one-parent GitHub commit. It waits for GitHub verification, checks that the verified commit still has the exact approved message, tree, and parent, rechecks the recorded author and live PR identity, and atomically updates the head with the recorded old OID and `force: false`. It then reconciles the normal required workflows, CodeQL, and validation-only Advisor run at the new SHA. Every validation workflow is dispatched from `main`, verifies that the event commit and workflow definition use one trusted workflow revision, and treats the recorded PR base SHA and generated SHA only as validation inputs. An exact existing attempt run is retained, a missing run receives a durable per-workflow check-run claim before dispatch, and duplicate or ambiguous evidence fails closed. The Advisor specialist fetch is independently pinned to that generated head and base. After every trusted workflow, CodeQL job, Advisor specialist, and exact generated-tree test succeeds, a separate trusted job that never checks out or executes PR code writes the required `changes`, `checks`, `commit-lint`, `dco-check`, and `check-hash` check runs onto the generated SHA. Each attestation is bound to the attempt and the canonical successful workflow job URL; no required success is reported before all validation is green.

`Automation / PR Review Advisor Repair Reconciliation` is the only supported workflow recovery path after validation. It is manual, uses the same non-cancelable per-PR concurrency group and protected publication environment, and requires the exact short-lived validation artifact from the original completed repair run. It never receives a model credential, starts OpenShell, invokes Pi, or recomputes a patch. The deterministic publisher either applies the original compare-and-swap update or recognizes that its exact verified commit is already the live head, then dispatches only missing generated-head validation workflows. Any unrelated live head, changed receipt identity, expired or substituted artifact, or duplicate validation run fails closed.

Every privileged job limits its trusted workflow-code checkout to reviewed automation helper and policy paths through a credential-free sparse checkout. The PR source checkout remains data only and never supplies workflow code. The final check reporter has `checks: write` but no PR checkout, model credential, source-write permission, or untrusted execution step.

## Maintainer setup and dispatch

Before enabling Phase 1, configure `advisor-repair-publication` as a protected GitHub environment that requires maintainer approval and permits deployments only from `main`. The workflow's `environment` field selects that environment; it does not configure the repository protection rules. Trusted code additionally limits Phase 1 to same-repository PRs authored by the current pilot, `cjagwani`. The pilot author must have maintain or admin permission. Forks and every other author fail before publication. Set the repository variable `ADVISOR_REPAIR_PHASE1_ENABLED` to `true` only after confirming those rules.

Phase 1 reuses the Advisor's [`PR_REVIEW_ADVISOR_API_KEY` repository secret](../pr-review-advisor/README.md#required-secret). Only the trusted repair lifecycle step reads the secret. The job-local OpenShell gateway holds the credential during model inference, and the lifecycle stops the gateway after normal success or failure. Pi, validation, publication, and artifacts never receive the secret. The repository secret remains configured for later Advisor runs.

Select the `main` branch in the workflow-dispatch form, then start an attempt through **Automation / PR Review Advisor Repair** with:

- the PR number and its full current head SHA;
- the successful Advisor run ID for that head;
- `product_scope_kind` set to `accepted-issue` or `maintainer-decision` and the corresponding
  issue number, URL, or recorded decision identifier in `product_scope_identity` (the workflow
  records this evidence; it does not independently verify that the reference accepts the repair
  scope);
- a JSON array of exact canonical Advisor finding IDs from the selected run; and
- `repository_egress_authorized` set to `true` for this dispatch.

Do not rerun the repair generation workflow. A new PR head requires a new maintainer dispatch and creates a different attempt identity. If a validated attempt is interrupted during or after publication, select the `main` branch and manually dispatch **Automation / PR Review Advisor Repair Reconciliation** with the original run ID, its short-lived validation artifact ID, PR number, and original source head SHA. Reconciliation never runs Pi again.

If generated-head validation fails after publication, the verification job uploads a durable receipt bound to the original source head, generated commit, base, attempt, failure class, and canonical failed gate when available. The workflow does not retry or revert automatically. For a failure proven to be infrastructure-only, rerun only the failed exact workflow in GitHub, then dispatch reconciliation from `main` with the original inputs. For a code, policy, or ambiguous evidence failure, leave reconciliation stopped and add a normal human-owned follow-up commit to the PR. Reconciliation and every later publication step compare the live head with the recorded source or generated commit, so neither recovery path can overwrite a contributor update.

## Rollout and kill switch

The repository variable `ADVISOR_REPAIR_PHASE1_ENABLED` is the emergency switch. Each dispatch must also set the boolean `repository_egress_authorized` input to explicitly authorize sending repository-derived context to NVIDIA's configured Advisor inference endpoint at `https://inference-api.nvidia.com/v1`. Repository maintain/admin permission does not imply that data-egress authorization. A disabled switch or missing egress acknowledgment records a disabled attempt receipt and stops before GitHub discovery, artifact download, OpenShell installation, or model use. The attempt receipt records both the original and triggering actors plus only a digest of the supplied finding IDs; it does not retain raw finding text. Workflow reruns fail closed after the audit step, and the neutral attempt claim prevents a separate dispatch from repeating the same exact attempt.

- **Phase 1 — protected manual publication:** implemented here behind an explicit exact-head maintainer dispatch, durable one-shot claim, protected environment, atomic publication, and exact-SHA validation.
- **Phase 2 — narrow automatic publication:** intentionally not implemented. A bounded Phase 1 conversation does not need cross-head identity. Automation across independent runs still requires a separately approved convergence contract, staging evidence for the complete flow, and a separate maintainer decision.

A resolver, trusted-validation, or generated-head CI failure stops the attempt. It does not trigger an automatic revert, another Pi turn, or a second repair attempt.

Local contract tests exercise the two-turn sandbox command boundary, commit-blind model context, real Git patch application, and tree reconstruction through the deterministic publisher while mocking GitHub authority. That is not the required staging-repository evidence. Keep the kill switch disabled until a staging run proves the verified GitHub commit, atomic branch update, exact-generated-head checks, and absence of a second repair attempt.

The accepted maintainer decision and bounded-conversation amendment on #10791 define the manual opt-in, eligible finding and path classes, two-turn in-attempt model boundary, limits, one-shot attempt identity, publisher boundary, and exact-SHA validation. #9774 is not a Phase 1 dependency. It closed without a stable cross-head repair-root contract, so a new PR head always requires a new manual decision and Phase 2 remains disabled pending a separate maintainer decision.

The Advisor emits nine independent Markdown reviews, native session traces, and canonical exact-head finding ledgers. Trusted selection binds every supplied finding ID to those ledgers and current review-thread state without parsing free-form model prose. Keep the production kill switch disabled until staging proves both the full publication and deterministic reconciliation paths.

Trusted runtime code compiles the six committed JSON Schemas and applies them before semantic identity and digest checks at every artifact boundary. The repository workflow-boundary checker validates the complete Phase 1, reconciliation, and generated-head authority graphs; focused mutation tests prove that it rejects credential/permission mixing, mutable artifacts, a second model repair, and missing exact-head verification.

## Artifacts

Each workflow dispatch can emit:

- `attempt-receipt.json`, including the emergency-switch decision and a digest of the supplied finding IDs;
- `selection.json`, `selection-authority.json`, `artifact-manifest.json`, and `repair-context.json`, bound to the live PR, exact Advisor artifact digests, canonical finding ledgers, and review-thread state; the repair job derives a commit-blind `repair-input.json` for Pi and never uploads `selection.json` into the sandbox;
- `proposal.json` and the trusted-host-generated `repair.patch`;
- `validation-receipt.json` and, only after successful validation, `validated.patch`;
- `publication-receipt.json`, including the source head, validated tree, verified commit, branch, and reconciled exact-head workflows;
- `generated-head-verification-receipt.json`, including the source head, generated commit, base, attempt identity, outcome, bounded failure class, and canonical failed gate when available.

Downstream jobs consume the exact `artifact-id` outputs from their producers. Same-run handoffs use the current run implicitly rather than accepting repository or run overrides; only the intentional cross-run Advisor input names its verified source run. Artifact names are labels for humans, not trust anchors.

After a stage produces its trusted result, it attempts to append a bounded job summary made only from trusted outcomes, hashes, numeric identities, and counts. The summary never renders finding prose, PR text, branch names, paths, or failure diagnostics supplied by untrusted content. If the summary file cannot be written, the stage logs a fixed warning and continues. Receipts, bound artifacts, and live GitHub state remain the authority.
